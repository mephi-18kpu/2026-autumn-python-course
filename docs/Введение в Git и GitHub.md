# Введение в Git и GitHub

Git хранит историю изменений проекта. GitHub хранит удалённые Git-репозитории и предоставляет средства совместной работы: доступ, Pull Request, обсуждение изменений и автоматические проверки.

## Основные понятия

- **Репозиторий** — проект вместе с историей его изменений.
- **Рабочая директория** — файлы проекта, которые сейчас находятся на компьютере.
- **Индекс** — набор изменений, подготовленных к следующему коммиту.
- **Коммит** — сохранённое состояние выбранных изменений с автором, временем и сообщением.
- **Ветка** — именованный указатель на линию истории коммитов.
- **HEAD** — указатель на текущее положение в истории, обычно на текущую ветку.
- **Удалённый репозиторий** — копия репозитория на сервере, например на GitHub.
- **origin** — стандартное имя основного удалённого репозитория.
- **Pull Request** — предложение объединить изменения одной ветки с другой на GitHub.

## Где находятся изменения

```text
Рабочая директория
    │ git add
    ▼
Индекс
    │ git commit
    ▼
Локальный репозиторий
    │ git push
    ▼
GitHub
```

`git add` не создаёт коммит и не отправляет файл на GitHub. Команда только подготавливает выбранное изменение.

## Создание локального репозитория

Для отдельного учебного примера:

```bash
mkdir git-demo
cd git-demo
git init
git status
```

Git хранит служебные данные в скрытой директории `.git`. В учебном процессе репозиторий обычно уже создан преподавателем, поэтому студент использует `git clone`, а не `git init`.

## Проверка изменений и создание коммита

```bash
git status
git diff
git add hello.py
git diff --cached
git commit -m "Добавлена первая версия программы"
git log --oneline
```

Назначение команд:

- `git status` показывает текущую ветку и состояния файлов;
- `git diff` показывает неподготовленные изменения уже отслеживаемых файлов;
- `git add` добавляет выбранные изменения в индекс;
- `git diff --cached` показывает содержимое будущего коммита;
- `git commit` создаёт коммит из индекса;
- `git log` показывает историю коммитов.

Коммит должен содержать одно законченное изменение. Сообщение должно объяснять его смысл.

Новый неотслеживаемый файл отображается в `git status`, но его содержимое не показывается обычной командой `git diff`. После `git add` содержимое такого файла можно проверить командой `git diff --cached`.

```text
Плохо:  fix
Плохо:  update
Хорошо: ЛР1: добавлена проверка входных данных
```

Не используйте `git add .`, не проверив `git status`: команда добавляет все изменения в текущей области.

## Удалённый репозиторий

Локальный репозиторий может быть связан с одним или несколькими другими Git-репозиториями. Такое именованное подключение называется `remote`.

```bash
git remote                    # показать имена подключений
git remote -v                 # показать имена и адреса
git remote add origin <URL>   # добавить подключение
```

`origin` — распространённое имя основного удалённого репозитория. Это имя не является адресом GitHub и не обозначает ветку. Вместо `origin` технически можно использовать другое имя, но в учебных репозиториях применяется `origin`.

Команда `git remote add origin <URL>` нужна, когда самостоятельно созданный локальный репозиторий требуется связать с удалённым. Если репозиторий получен через `git clone`, Git создаёт `origin` автоматически:

```bash
git clone <URL>       # получить существующий репозиторий
git fetch origin      # получить сведения и коммиты без слияния
git pull --ff-only    # получить изменения текущей ветки
git push              # отправить локальные коммиты
```

Команды `git fetch` и `git pull` обе получают данные из удалённого репозитория, но по-разному влияют на текущую работу.

`git fetch origin` загружает новые коммиты и обновляет локальные представления удалённых веток, например `origin/master`. При этом текущая локальная ветка, рабочие файлы и индекс не изменяются. После `fetch` можно сначала изучить полученные изменения:

```bash
git fetch origin
git log --oneline master..origin/master
git diff master..origin/master
```

Предположим, локальная ветка `master` находится на коммите `B`, а на GitHub уже появился коммит `C`:

```text
До git fetch:

master          A──B
origin/master   A──B
GitHub          A──B──C

После git fetch origin:

master          A──B
origin/master   A──B──C
```

Локальная ветка `master` и файлы остаются на состоянии `B`. Изменяется только информация о состоянии ветки на GitHub.

`git pull --ff-only` сначала получает данные, как `git fetch`, а затем перемещает текущую локальную ветку вперёд до состояния связанной удалённой ветки. Рабочие файлы при этом обновляются:

```text
После git pull --ff-only:

master          A──B──C
origin/master   A──B──C
```

Если изменения уже получены командой `git fetch`, применить их к текущей локальной ветке можно отдельно:

```bash
git status
git diff HEAD..origin/<имя-ветки>
git merge --ff-only origin/<имя-ветки>
```

Сначала следует убедиться с помощью `git status`, что выбрана нужная ветка и в рабочей директории нет несохранённых изменений. Команда `git diff` позволяет просмотреть разницу между текущим коммитом и полученным состоянием удалённой ветки. Команда `git merge --ff-only` применяет изменения только простым перемещением текущей ветки вперёд.

Например, для локальной ветки `master`:

```bash
git fetch origin
git diff HEAD..origin/master
git merge --ff-only origin/master
```

В простом случае команда `git pull --ff-only` выполняет ту же последовательность получения и применения изменений:

```text
git pull --ff-only = git fetch + git merge --ff-only
```

Параметр `--ff-only` разрешает только простое перемещение ветки вперёд. Если в локальной и удалённой ветках появились разные коммиты, команда завершится ошибкой и не создаст автоматическое слияние. Это позволяет сначала проверить ситуацию и выбрать правильный способ продолжения работы.

Если ветки разошлись, не следует выполнять обычный `git merge`, `git rebase` или команды перезаписи истории наугад. В учебном репозитории студент должен сохранить текущее состояние и обратиться к преподавателю.

Таким образом, `git fetch origin` используют, когда нужно безопасно обновить сведения об удалённых ветках перед просмотром, сравнением или переключением. `git pull --ff-only` используют, когда нужно обновить уже выбранную локальную ветку и изменить рабочие файлы до актуального удалённого состояния. Обычная команда `git pull` без `--ff-only` может выполнить слияние или перебазирование в зависимости от конфигурации, поэтому в учебных инструкциях она без необходимости не используется.

Коммиты создаются локально, поэтому для `git commit` интернет не требуется. Интернет нужен для обмена данными с GitHub.

В учебном репозитории организации студент проверяет готовое подключение командой `git remote -v`, но не добавляет, не удаляет и не меняет `remote` самостоятельно.

## Настройка личного компьютера для работы с GitHub

Этот раздел относится только к личному компьютеру и личному аккаунту GitHub. На аудиторном компьютере используется уже настроенный аккаунт рабочего места, поэтому подключать там личный аккаунт нельзя.

Настройка состоит из трёх независимых действий:

1. указать автора локальных коммитов;
2. добавить адрес удалённого репозитория;
3. авторизоваться на GitHub при первой операции, требующей доступа.

### Автор локальных коммитов

На личном компьютере имя и адрес электронной почты можно настроить для всех локальных репозиториев:

```bash
git config --global user.name "ИМЯ_ИЛИ_GITHUB_LOGIN"
git config --global user.email "EMAIL_ИЗ_GITHUB_ИЛИ_NOREPLY"
```

Используйте адрес, подтверждённый в GitHub, либо выданный GitHub адрес `noreply` из раздела **Settings → Emails**. Тогда GitHub сможет связать коммиты с личным аккаунтом. Эти параметры определяют автора коммита, но не предоставляют доступ к GitHub.

Проверка настройки:

```bash
git config --global --get user.name
git config --global --get user.email
```

### Подключение удалённого репозитория

Если репозиторий уже создан на GitHub, проще всего сразу клонировать его:

```bash
git clone https://github.com/<логин>/<репозиторий>.git
cd <репозиторий>
```

Если локальный репозиторий был создан командой `git init`, а пустой удалённый репозиторий — через сайт GitHub, подключите его отдельно:

```bash
git remote add origin https://github.com/<логин>/<репозиторий>.git
git remote -v
git push -u origin HEAD
```

Команда `git remote add origin <URL>` только сохраняет адрес в локальной конфигурации. Она не обращается к GitHub и не выполняет авторизацию. Команда `git push -u origin HEAD` отправляет текущую ветку и настраивает её связь с одноимённой удалённой веткой.

### Авторизация на GitHub

На Windows рекомендуется установить актуальную версию Git for Windows с компонентом Git Credential Manager. При первом `push` Git Credential Manager предложит войти в GitHub через браузер. Необходимо авторизоваться под своим личным аккаунтом и подтвердить доступ. Если вход уже был выполнен и учётные данные сохранены, браузер может не открыться повторно.

Пароль аккаунта GitHub нельзя использовать как пароль для Git-команд. Не создавайте и не вводите токен вручную, если используется браузерная авторизация через Git Credential Manager. После успешного входа данные доступа сохраняются в диспетчере учётных данных операционной системы и автоматически используются командами `git fetch`, `git pull` и `git push`.

Дополнительная информация: [настройка Git](https://docs.github.com/ru/get-started/git-basics/set-up-git) и [сохранение учётных данных GitHub в Git](https://docs.github.com/ru/get-started/git-basics/caching-your-github-credentials-in-git).

## Ветки

Создание и переключение на новую ветку:

```bash
git switch -c feature/greeting
```

Просмотр текущей ветки:

```bash
git branch --show-current
```

Переключение на существующую ветку:

```bash
git switch master
```

Ветка не является отдельной копией всей директории. Она указывает на определённый коммит и перемещается при создании новых коммитов.

## Слияние

Чтобы включить изменения ветки `feature/greeting` в текущую ветку:

```bash
git switch master
git merge feature/greeting
```

Git выполняет слияние автоматически, если изменения совместимы. Если две ветки по-разному изменили один участок файла, возникает конфликт.

```text
<<<<<<< HEAD
текущая версия
=======
версия из другой ветки
>>>>>>> feature/greeting
```

Необходимо выбрать правильное содержимое, удалить маркеры, проверить файл и завершить слияние:

```bash
git diff
git add <файл>
git status
git commit
```

Если правильный вариант непонятен, слияние можно отменить:

```bash
git merge --abort
```

## Pull Request

Pull Request создаётся на GitHub и используется для:

- просмотра различий между ветками;
- обсуждения и проверки работы;
- запуска автоматических проверок;
- принятия решения о слиянии.

После замечаний работу исправляют в той же исходной ветке. Новые коммиты автоматически появляются в открытом Pull Request.

# Работа с репозиториями `mephi-18kpu`

Инструкции конкретного курса дополняют общие правила и имеют приоритет.

## Разрешённая область работы

Для каждого задания студент работает только в отдельной рабочей ветке и своей директории:

```text
Ветка задания:           submissions/<задание>
Ветка отчётной работы:   student-submission/<задание>/<группа>/student-<номер>
Постоянная ветка:        student/<группа>/student-<номер>
Личная директория:       <группа>/student-<номер>/
```

Пример:

```text
Ветка задания:           submissions/lab-01
Ветка отчётной работы:   student-submission/lab-01/b24-601/student-07
Постоянная ветка:        student/b24-601/student-07
Личная директория:       b24-601/student-07/
```

Основная ветка учебного репозитория называется `master`. Она содержит задания, инструкции и материалы преподавателей. Все удалённые ветки учебного процесса заранее создаёт администратор организации. Ветки `submissions/<задание>` создаются независимо друг от друга, а персональные ветки отчётной работы создаются от сохранённого исходного commit соответствующего задания. Студенческий код в `master` не переносится.

## Первоначальное клонирование

```bash
cd "D:/Study"
git clone https://github.com/mephi-18kpu/2026-autumn-python-course.git
cd 2026-autumn-python-course
git remote -v
git status
```

Адрес `origin` должен указывать на нужный репозиторий организации `mephi-18kpu`.

## Идентификация на аудиторном компьютере

```bash
git config --local --get user.name
git config --local --get user.email
```

Каждому физическому аудиторному компьютеру соответствует один технический аккаунт GitHub независимо от курса и локальной учётной записи Windows. В каждом клоне настроен соответствующий технический автор, например `a220-workstation-pc-7`. Аккаунт и автор коммита идентифицируют компьютер, но не конкретного студента. Студент определяется по рабочей ветке задания, личной директории и данным преподавателя.

Студент не меняет локальную идентификацию, адрес `origin`, ключи или другие параметры доступа. На аудиторных компьютерах нельзя использовать `git config --global`, подключать личный аккаунт GitHub или переносить данные аккаунта рабочего места на другое устройство.

## Подключение ветки отчётной работы

До начала задания администратор создаёт на GitHub общую ветку `submissions/<задание>` и персональные ветки студентов от одного согласованного состояния `master`. Студент подключает уже существующую удалённую ветку:

```bash
git fetch origin
git switch --track origin/student-submission/lab-01/b24-601/student-07
```

Если ветка уже существует локально:

```bash
git switch student-submission/lab-01/b24-601/student-07
git pull --ff-only
```

Если удалённой ветки нет, её имя не совпадает с выданным идентификатором или Git предлагает создать новую ветку, остановитесь и обратитесь к преподавателю. Студент не создаёт удалённые ветки самостоятельно; преподаватель передаёт запрос администратору, который создаёт пропущенную ветку от сохранённого исходного commit задания.

Не копируйте имена веток из примера без изменений.

## Начало каждого занятия

```bash
cd 2026-autumn-python-course
git status
git branch --show-current
git switch student-submission/lab-01/b24-601/student-07
git pull --ff-only
```

Текущей должна быть рабочая ветка выполняемого задания. `git pull` выполняется только при отсутствии незакоммиченных изменений.

## Сохранение и публикация работы

```bash
git status
git diff
git add b24-601/student-07/solution.py
git diff --cached
git commit -m "ЛР1: добавлено решение первого задания"
git push
```

Перед `push` обязательно проверьте текущую ветку. Если upstream отсутствует, не создавайте удалённую ветку через `git push -u`: проверьте имя ветки и обратитесь к преподавателю.

## Сдача через Pull Request

Преподаватель сообщает имя ветки задания, например `submissions/lab-01`, срок и ожидаемый состав работы.

На GitHub выберите:

- **base** — ветку задания `submissions/<задание>`;
- **compare** — ветку отчётной работы `student-submission/<задание>/<группа>/student-<номер>`.

Перед созданием Pull Request проверьте вкладку **Files changed**. Изменения должны находиться только в вашей личной директории.

После замечаний:

1. Исправьте файлы в той же рабочей ветке задания.
2. Создайте новые коммиты.
3. Выполните `git push`.

Новый Pull Request создавать не нужно. Студент не выполняет merge и не отправляет изменения непосредственно в ветку задания. После принятия преподаватель выполняет squash merge.

## После принятия задания

Ветка принятого задания не удаляется, но больше не используется. Для следующего задания администратор создаёт новую независимую ветку `submissions/lab-02` от актуального согласованного состояния `master` и заранее создаёт персональную ветку отчётной работы:

```text
student-submission/lab-02/b24-601/student-07
```

Студент подключает выданную ветку и не создаёт её самостоятельно от предыдущей студенческой ветки или от `submissions` другого задания.

## Обновление материалов после начала задания

Не объединяйте в рабочую ветку обновившуюся `submissions/<задание>`: после начала приёма там могут находиться работы других студентов. Не объединяйте `master` без прямого указания преподавателя.

Если преподаватель изменил материалы после начала задания, следуйте отдельной инструкции. Если нежелательное слияние уже начато, не завершайте его самостоятельно; выполните `git merge --abort` или обратитесь к преподавателю.

## Запрещённые действия

Студентам запрещено:

- отправлять изменения непосредственно в `master` и `submissions/...`;
- создавать на GitHub любые новые ветки;
- самостоятельно объединять Pull Request;
- использовать ветку предыдущего задания для новой работы;
- объединять `master` или обновившуюся `submissions/<задание>` без прямого указания преподавателя;
- изменять чужие ветки и директории;
- применять `git push --force` и переписывать опубликованную историю;
- изменять адрес репозитория, техническую идентификацию, аккаунт рабочего места, ключи и настройки доступа;
- добавлять пароли, токены, приватные ключи и другие секреты;
- размещать чужую работу под своим именем.

## Безопасная диагностика ошибок

Перед исправлением выполните:

```bash
git status
git branch --show-current
git log --oneline --decorate -10
```

Прочитайте полный текст ошибки. Не применяйте force-push, не удаляйте ветки и не запускайте `reset --hard`, пока полезные изменения не сохранены.

Обратитесь к преподавателю, если изменение уже отправлено в `master` или чужую ветку, возникла проблема с доступом, обнаружены чужие изменения либо безопасный способ исправления непонятен.

Никому не отправляйте пароль, токен, приватный SSH-ключ, recovery codes или коды двухфакторной аутентификации.

## Полезные команды просмотра

```bash
git status
git branch --show-current
git branch --all
git log --oneline --decorate --graph -20
git diff
git diff --cached
git remote -v
```
