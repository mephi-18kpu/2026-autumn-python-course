# Введение в Git и GitHub

Git хранит историю изменений проекта. GitHub хранит удалённые Git-репозитории и предоставляет средства совместной работы: доступ, Pull Request, обсуждение изменений и автоматические проверки.

## Основные понятия

- **Репозиторий** — проект вместе с историей его изменений.
- **Рабочая директория** — файлы проекта, которые сейчас находятся на компьютере.
- **Индекс** — набор изменений, подготовленных к следующему коммиту.
- **Коммит** — сохранённое состояние выбранных изменений с автором, временем и сообщением.
- **Ветка** — именованный указатель на линию истории коммитов.
- **HEAD** — указатель на текущее положение в истории, обычно на текущую ветку.
- **Удалённый репозиторий** — копия репозитория на сервере, например на GitHub.
- **origin** — стандартное имя основного удалённого репозитория.
- **Pull Request** — запрос на объединение изменений одной ветки с другой на GitHub.

## Где находятся изменения

```text
Рабочая директория
    │ git add
    ▼
Индекс
    │ git commit
    ▼
Локальный репозиторий
    │ git push
    ▼
GitHub
```

`git add` не создаёт коммит и не отправляет файл на GitHub. Команда только подготавливает выбранное изменение.

## Создание локального репозитория

Для отдельного учебного примера:

```bash
mkdir git-demo
cd git-demo
git init
git status
```

Git хранит служебные данные в скрытой директории `.git`. В учебном процессе репозиторий обычно уже создан преподавателем, поэтому студент использует `git clone`, а не `git init`.

## Проверка изменений и создание коммита

```bash
git status
git diff
git add hello.py
git diff --cached
git commit -m "Добавлена первая версия программы"
git log --oneline
```

Назначение команд:

- `git status` показывает текущую ветку и состояния файлов;
- `git diff` показывает неподготовленные изменения уже отслеживаемых файлов;
- `git add` добавляет выбранные изменения в индекс;
- `git diff --cached` показывает содержимое будущего коммита;
- `git commit` создаёт коммит из индекса;
- `git log` показывает историю коммитов.

Коммит должен содержать одно законченное изменение. Сообщение должно объяснять его смысл.

Новый неотслеживаемый файл отображается в `git status`, но его содержимое не показывается обычной командой `git diff`. После `git add` содержимое такого файла можно проверить командой `git diff --cached`.

Пример текстовых обозначений коммитов:

```text
Плохо:  fix
Плохо:  update
Хорошо: ЛР1: добавлена проверка входных данных
```

Не используйте `git add .`, не проверив `git status`: команда добавляет все изменения в текущей области, что может быть нежелательно в некоторых случаях.

## Удалённый репозиторий

Локальный репозиторий может быть связан с одним или несколькими другими Git-репозиториями. Такое именованное подключение называется `remote`.

```bash
git remote                    # показать имена подключений
git remote -v                 # показать имена и адреса
git remote add origin <URL>   # добавить подключение
```

`origin` — распространённое имя основного удалённого репозитория. Это имя не является адресом GitHub и не обозначает ветку. Вместо `origin` технически можно использовать другое имя, но в учебных репозиториях применяется `origin`.

Команда `git remote add origin <URL>` нужна, когда самостоятельно созданный локальный репозиторий требуется связать с удалённым. Если репозиторий получен через `git clone`, Git создаёт `origin` автоматически:

```bash
git clone <URL>       # получить существующий репозиторий
git fetch origin      # получить сведения и коммиты без слияния
git pull --ff-only    # получить изменения текущей ветки
git push              # отправить локальные коммиты
```

Команды `git fetch` и `git pull` обе получают данные из удалённого репозитория, но по-разному влияют на текущую работу.

`git fetch origin` загружает новые коммиты и обновляет локальные представления удалённых веток, например `origin/master`. При этом текущая локальная ветка, рабочие файлы и индекс не изменяются. После `fetch` можно сначала изучить полученные изменения:

```bash
git fetch origin
git log --oneline master..origin/master
git diff master..origin/master
```

Предположим, локальная ветка `master` находится на коммите `B`, а на GitHub уже появился коммит `C`:

```text
До git fetch:

master          A──B
origin/master   A──B
GitHub          A──B──C

После git fetch origin:

master          A──B
origin/master   A──B──C
GitHub          A──B──C
```

Локальная ветка `master` и файлы остаются на состоянии `B`. Изменяется только информация о состоянии ветки на GitHub.

`git pull --ff-only` сначала получает данные, как `git fetch`, а затем перемещает текущую локальную ветку вперёд до состояния связанной удалённой ветки. Рабочие файлы при этом обновляются:

```text
После git pull --ff-only:

master          A──B──C
origin/master   A──B──C
GitHub          A──B──C
```

Если изменения уже получены командой `git fetch`, применить их к текущей локальной ветке можно отдельно:

```bash
git status
git diff HEAD..origin/<имя-ветки>
git merge --ff-only origin/<имя-ветки>
```

Сначала следует убедиться с помощью `git status`, что выбрана нужная ветка и в рабочей директории нет несохранённых изменений. Команда `git diff` позволяет просмотреть разницу между текущим коммитом и полученным состоянием удалённой ветки. Команда `git merge --ff-only` применяет изменения только простым перемещением текущей ветки вперёд.

Например, для локальной ветки `master`:

```bash
git fetch origin
git diff HEAD..origin/master
git merge --ff-only origin/master
```

В простом случае команда `git pull --ff-only` выполняет ту же последовательность получения и применения изменений:

```text
git pull --ff-only = git fetch + git merge --ff-only
```

Параметр `--ff-only` разрешает только простое перемещение ветки вперёд. Если в локальной и удалённой ветках появились разные коммиты, команда завершится ошибкой и не создаст автоматическое слияние. Это позволяет сначала проверить ситуацию и выбрать правильный способ продолжения работы.

Если ветки разошлись, не следует выполнять обычный `git merge`, `git rebase` или команды перезаписи истории наугад. Сначала нужно выяснить, какие коммиты появились в каждой ветке, и выбрать подходящий способ объединения.

Таким образом, `git fetch origin` используют, когда нужно безопасно обновить сведения об удалённых ветках перед просмотром, сравнением или переключением. `git pull --ff-only` используют, когда нужно обновить уже выбранную локальную ветку и изменить рабочие файлы до актуального удалённого состояния. Обычная команда `git pull` без `--ff-only` может выполнить слияние или перебазирование в зависимости от конфигурации, поэтому в учебных инструкциях она без необходимости не используется.

Коммиты создаются локально, поэтому для `git commit` интернет не требуется. Интернет нужен для обмена данными с GitHub.

## Настройка личного компьютера для работы с GitHub

Этот раздел относится к личному компьютеру и личному аккаунту GitHub. Правила работы с учебными репозиториями `mephi-18kpu` приведены отдельно в [единой инструкции](https://github.com/mephi-18kpu/common-manuals/blob/master/students/repository-workflow.md).

Подготовка состоит из четырёх действий:

1. указать автора локальных коммитов;
2. создать пустой репозиторий на GitHub;
3. создать и связать с ним локальный репозиторий;
4. авторизоваться на GitHub при первой операции, требующей доступа.

### Автор локальных коммитов

На личном компьютере имя и адрес электронной почты можно настроить для всех локальных репозиториев:

```bash
git config --global user.name "ИМЯ_ИЛИ_GITHUB_LOGIN"
git config --global user.email "EMAIL_ИЗ_GITHUB_ИЛИ_NOREPLY"
git config --global init.defaultBranch master
```

Используйте адрес, подтверждённый в GitHub, либо выданный GitHub адрес `noreply` из раздела **Settings → Emails**. Тогда GitHub сможет связать коммиты с личным аккаунтом. Параметры `user.name` и `user.email` определяют автора коммита, но не предоставляют доступ к GitHub. Параметр `init.defaultBranch` задаёт имя начальной ветки для новых репозиториев, создаваемых командой `git init`; в рамках курса используется `master`.

Проверка настройки:

```bash
git config --global --get user.name
git config --global --get user.email
git config --global --get init.defaultBranch
```

### Авторизация на GitHub

Чтобы явно авторизовать локальные Git-команды для работы с нужным аккаунтом GitHub, выполните:

```bash
git credential-manager github login --username "ЛОГИН_GITHUB" --browser
```

Git Credential Manager откроет браузер. Авторизуйтесь под указанным личным аккаунтом GitHub и подтвердите доступ. После успешного входа учётные данные будут сохранены в диспетчере учётных данных операционной системы. Если вход уже был выполнен и подходящие данные сохранены, браузер может не открыться повторно.

Пароль аккаунта GitHub нельзя использовать как пароль для Git-команд. Не создавайте и не вводите токен вручную, если используется браузерная авторизация через Git Credential Manager. После успешного входа данные доступа сохраняются в диспетчере учётных данных операционной системы и автоматически используются командами `git fetch`, `git pull` и `git push`.

Дополнительная информация: [настройка Git](https://docs.github.com/ru/get-started/git-basics/set-up-git) и [сохранение учётных данных GitHub в Git](https://docs.github.com/ru/get-started/git-basics/caching-your-github-credentials-in-git).

### Создание собственного репозитория и первая публикация

Сначала создайте пустой репозиторий на GitHub:

1. Войдите в личный аккаунт GitHub и выберите **New repository**.
2. Укажите имя репозитория и его видимость: **Public** или **Private**.
3. Не добавляйте `README`, `.gitignore` и лицензию через GitHub, если проект уже создаётся локально: удалённый репозиторий должен остаться пустым.
4. Нажмите **Create repository** и скопируйте HTTPS-адрес вида `https://github.com/<логин>/<репозиторий>`.

Затем создайте локальную директорию проекта и инициализируйте в ней Git-репозиторий. Во всех репозиториях курса основной веткой является `master`:

```bash
mkdir <репозиторий>
cd <репозиторий>
git init
```

Создайте в редакторе файл `README.md`, сохраните его и выполните первую публикацию:

```bash
git status
git add README.md
git diff --cached
git commit -m "Добавлен README"
git remote add origin https://github.com/<логин>/<репозиторий>
git remote -v
git push -u origin master
```

Параметр `-b` позволяет явно задать имя начальной ветки при создании репозитория, например `git init -b master`. Указывать его необязательно: если ранее выполнена глобальная настройка `git config --global init.defaultBranch master`, команда `git init` уже создаст ветку `master`. Проверьте имя командой `git branch --show-current`. Если Git создал ветку с другим именем, до первого push переименуйте её командой `git branch -M master`.

Команда `git remote add origin <URL>` сохраняет адрес удалённого репозитория. Первый `git push -u origin master` отправляет коммиты на GitHub и связывает локальную ветку `master` с удалённой, поэтому в дальнейшем достаточно выполнять `git push` и `git pull --ff-only`.

Если локальный проект уже существует, перейдите в его директорию и начните последовательность с `git init`. Если репозиторий уже содержит директорию `.git`, повторно выполнять `git init` не нужно.

Если репозиторий уже создан на GitHub вместе с начальными файлами или коммитами, не связывайте с ним независимо созданную локальную историю. Сразу клонируйте репозиторий:

```bash
git clone https://github.com/<логин>/<репозиторий>
cd <репозиторий>
```

## Ветки

Создание и переключение на новую ветку:

```bash
git switch -c feature/greeting
```

Если ветка уже существует в удалённом репозитории, создайте одноимённую локальную ветку и сразу свяжите её с удалённой с помощью флага `--track`:

```bash
git switch -c feature/greeting --track origin/feature/greeting
```

Флаг `--track` настраивает для локальной ветки upstream — связанную удалённую ветку, относительно которой выполняются `git pull` и `git push` без явного указания имени удалённого репозитория и ветки. Удалённая ветка должна существовать и быть известна локальному Git; при необходимости сведения о ней предварительно получают командой `git fetch origin`.

Просмотр текущей ветки:

```bash
git branch --show-current
```

Переключение на существующую ветку:

```bash
git switch master
```

Ветка не является отдельной копией всей директории. Она указывает на определённый коммит и перемещается при создании новых коммитов.

## Слияние

Предположим, ветки `master` и `feature/greeting` разошлись после коммита `B`:

```text
      C───D  feature/greeting
     /
A───B───E───F  master
```

Изменения можно объединить с помощью `merge` или предварительно перенести на актуальное состояние `master` с помощью `rebase`. При одинаковом разрешении возможных конфликтов эти способы позволяют получить одинаковое содержимое файлов, но формируют разную историю коммитов.

### Merge

Чтобы включить изменения ветки `feature/greeting` в текущую ветку:

```bash
git switch master
git merge feature/greeting
```

Если ветки разошлись, Git создаст merge-коммит `M` с двумя родительскими коммитами и сохранит исходную структуру истории:

```text
      C───D───────────┐
     /                │
A───B───E───F─────────M  master
```

Если после отделения `feature/greeting` в `master` не появилось новых коммитов, отдельный merge-коммит не требуется: Git выполнит fast-forward и просто переместит `master` вперёд.

Git выполняет слияние автоматически, если изменения совместимы. Если две ветки по-разному изменили один участок файла, возникает конфликт.

```text
<<<<<<< HEAD
текущая версия
=======
версия из другой ветки
>>>>>>> feature/greeting
```

Необходимо выбрать правильное содержимое, удалить маркеры, проверить файл и завершить слияние:

```bash
git diff
git add <файл>
git status
git commit
```

Если правильный вариант непонятен, слияние можно отменить:

```bash
git merge --abort
```

Преимущество `merge` — сохранение исходных коммитов и реальной структуры ветвления. Это безопасный вариант для опубликованных и совместно используемых веток, потому что существующая история не переписывается. Недостаток — при большом количестве веток история может содержать много merge-коммитов и становиться сложнее для чтения.

### Rebase

Команда `rebase` переносит коммиты текущей ветки на другую основу. Для ветки `feature/greeting` выполните:

```bash
git switch feature/greeting
git rebase master
```

Git последовательно заново применит изменения коммитов `C` и `D` после актуального коммита `F`. Поскольку это будут новые коммиты с другими родителями, их идентификаторы изменятся на `C'` и `D'`:

```text
A───B───E───F  master
             \
              C'───D'  feature/greeting
```

После успешного `rebase` ветку можно включить в `master` простым fast-forward:

```bash
git switch master
git merge --ff-only feature/greeting
```

Итоговая история будет линейной:

```text
A───B───E───F───C'───D'  master
```

Если при `rebase` возник конфликт, исправьте файл, добавьте его в индекс и продолжите перенос:

```bash
git add <файл>
git rebase --continue
```

Отменить незавершённый перенос можно командой:

```bash
git rebase --abort
```

Преимущество `rebase` — линейная и компактная история без дополнительного merge-коммита. Это удобно для локальной ветки одного разработчика перед её объединением. Недостаток — изменение идентификаторов переносимых коммитов: перебазирование уже опубликованной и используемой другими людьми ветки нарушает их историю и обычно требует принудительной отправки. Поэтому не выполняйте `rebase` для совместно используемых или уже принятых веток.

### Сравнение

| Критерий | `merge` | `rebase` |
| --- | --- | --- |
| Форма истории | Сохраняет ветвление и при расхождении создаёт merge-коммит | Создаёт линейную историю |
| Исходные коммиты | Не изменяет | Пересоздаёт переносимые коммиты с новыми идентификаторами |
| Опубликованные ветки | Безопасен для совместной работы | Не рекомендуется после публикации ветки |
| Разрешение конфликтов | Обычно выполняется один раз при слиянии | Может потребоваться отдельно для каждого переносимого коммита |
| Когда применять | Нужно сохранить реальную историю разработки или объединить общую ветку | Нужно подготовить собственную локальную ветку и получить линейную историю |

Универсально лучшего способа нет. Используйте `merge`, если история уже опубликована, с веткой работают несколько человек или важно сохранить момент объединения. Используйте `rebase`, если ветка ещё локальная, принадлежит одному разработчику и её коммиты нужно аккуратно расположить поверх актуального состояния основной ветки.

## Pull Request

Pull Request создаётся на GitHub и используется для:

- просмотра различий между ветками;
- обсуждения и проверки работы;
- запуска автоматических проверок, если они настроены в репозитории;
- принятия решения о слиянии.

После замечаний работу исправляют в той же исходной ветке. Новые коммиты автоматически появляются в открытом Pull Request.
